# Govern 反馈案例生命周期

## 存储与使用分离

沿用原有 `failure_cases`、`govern-feedback` 检查点和候选状态机，不新建另一套案例数据库。
原始 Finding、反馈修订和证据引用持续保存；生成器不删除历史，也不把“生成过候选”写成缺陷已解决。
旧 `resolved` 标志用于原入口的消费语义，不用它冒充 Govern 的问题解决状态。

Govern 使用候选 `lineage` 记录 feedback_ids、failure_case_ids、case_fingerprints、
输入摘要 Hash、抽样限制和选中数量。数据库中的候选记录是持久使用账本，不依赖进程内缓存。

- 同一 Finding 仅使用最新反馈；改为有效后不再用旧误报反馈生成候选。
- 当前基线下尚在审批/评测的候选占用对应案例，重复点击不重复调用模型。
- ACTIVE/SUPERSEDED 案例视为已被发布版本消费，不再触发相同优化；这不是缺陷已被实测解决的证明。
- REJECTED/ROLLED_BACK 允许人工重试。基线或策略源已变化的未发布候选不永久占用案例。
- 相同 Finding、阶段、类别和原因的重复反馈有相同指纹；真正改变原因的修订可重新参与。
- 模型/工具失败、进程中断且没有保存候选时，案例仍可重试。

## 有界上下文

失败记录按租户进行 ID 游标分页，不再只扫描最近 200 个任务。每次建立最多 100 个
符合条件的待处理案例窗口，最多处理三个阶段/原因分组。
每组采用仓库轮询，最多 10 个代表案例，序列化 JSON 不超过 24,000 UTF-8 字节。
这是案例上下文字节限额，不是精确 Token 计数；Pi 的共享预算继续约束完整模型请求。
长文本、深层对象和大数组只提供有界摘录；完整记录仍在原案例及任务检查点中。
未被本轮抽中的案例不会被标为已消费，可在后续轮次进入上下文。

受保护仓库及相同 diff 的评测数据、评测任务、无明确阶段的反馈和已识别的工程故障不进入策略生成。
分组是确定性的阶段/反馈类型/原因归组，并非已实现语义聚类。

## 并发与治理边界

当前进程内队列部署使用非阻塞单飞锁避免同一进化实例并发调用模型。
该锁不是跨进程分布式租约；多 worker 自动生成需要补充数据库生成租约及失效 fencing。
原有候选评测租约、评测门禁、人工审批和发布/回滚状态机继续沿用。
反馈修订不会自动撤销已经生成的候选；审批人需核对其冻结来源，后续可加入发布前来源新鲜度门禁。

## 阈值自动触发（默认关闭）

策略中心可配置开关、每阶段阈值（1..100，默认10）和最小间隔（1..10080分钟，默认1440）。
后台单工作线程每30秒检查，反馈保存及配置变更会唤醒检查，启动时从已有反馈恢复租户列表。
仅达到阈值的阶段进入生成；手动生成不受该阈值限制。双方沿用同一生成单飞锁及案例使用账本。
每次生成尝试后持久保存时间、候选 ID、评测状态、计数和失败类型；失败也进入冷却，重启不清零。

自动路径生成候选后调用既有 evaluate（Validation/Holdout），不调用 approve、shadow、activate。
缺少评测集或评测失败会保留候选及错误状态，必须人工处理，不假定评测通过。
开关关闭阻止后续步骤；已经发送的模型请求可能继续完成，不保证立即取消计费。

真实模型自动调用还有独立的受信服务端环境锁 `GOVERN_AUTO_EVOLUTION_MODEL_CALLS=1`，
默认没有授权。前端配置不能修改此锁；阈值满足但未授权时，只记录 waiting_authorization，
不发送案例、不调用生成或评测模型。后续显式授权后需重启服务加载环境变量。
当前部署仍是单进程本地工作线程，不支持跨 worker 的自动生成互斥。

测试使用本地 fake bridge/假评测器，不调用真实模型，也不修改用户的真实反馈。
